# GenOS Knowledge Capture

GenOS 현장 작업(FDE)에서 *한 번 배운 걸 다음 세션·다음 고객사에서 다시 파헤치지 않도록* 만드는 개인 스킬이다. AI의 세션 기억은 끊기지만, vault에 원자적 노트로 남기고 **허브(`00 GenOS 시작하기`, 고객사별 `00 <고객사> 시작하기`)와 그 허브의 처음 읽는 순서에 엮어두면** 새 세션이 필요한 노트를 발견하고, 처음 읽을 순서까지 빠르게 잡는다.

이 스킬은 사용자 개인 자산(`~/.claude/skills/`)이다. **회사 레포의 `.claude/skills/genos-*`(genos-session-close 등)는 회사 공유 자산이라 절대 건드리지 않는다.** 세션 상태는 회사 HANDOFF가, 재사용 지식은 이 스킬이 담당한다 — 둘은 분리된 관심사다.

> 공통 규칙: `~/.dotfiles/vault/references/note-rules.md` (Projects frontmatter 순서, 태그 형식과 허용 분야, 저장 후 `vk register`, 허브 대응표). 노트 본문 형식(이 스킬 고유의 source 식별자, 7섹션 spine, Mermaid·문체 규칙)은 [references/note-format.md](references/note-format.md)에 있다. 워크플로우 4단계에서 두 파일을 읽고 따른다.

## 핵심 원칙 (왜 이렇게 하나)

**① 온보딩 가속의 실체는 허브 + 처음 읽는 순서다.** "그래프뷰가 예쁜 것"이 아니라 *작은 진입점(허브)을 먼저 읽고, 거기서 오늘 필요한 노트를 발견한 뒤, 허브의 `## 처음 읽는 순서`로 무엇부터 볼지 정하는 것*이다. AI는 Obsidian 그래프를 순회하지 못한다. 그래서 이 스킬은 늘 세 가지를 함께 한다: 원자적 노트 작성 + **허브 등록(`vk register`)** + **처음 읽는 순서 반영 검토**. 허브에 안 걸린 노트는 발견되지 않고, 읽는 순서에 안 걸린 노트는 처음 보는 사람이 언제 읽어야 할지 모른다.

**② 재사용 가능한 일반화만 담는다.** 토큰 절감은 "재탐색(re-grep·재독)을 대체할 때 + 선택적으로 1~2개만 읽을 때"만 생긴다. 그러니 노트엔 패턴·함정·결정만 담고, "오늘 무슨 파일 고쳤는지" 같은 휘발성 상태는 vault에 넣지 않는다(노이즈만 쌓인다).

**③ 1차 독자는 "이 기술을 처음 보는 사람"이다.** 노트는 입사 직후의 동료나 다음 세션의 AI가 *이 문서 한 장만으로* 개념을 잡고 GenOS에서의 위치를 이해할 수 있는 **자기완결 field note**다. 먼저 사람이 읽는 흐름으로 열고, 판단·분기·함정은 bullet·표·Mermaid로 스캔 가능하게 만든다. 형식 상세는 references/note-format.md.

## 3계층 — 무엇을 캡처하고 무엇을 버리나

캡처 후보가 생기면 먼저 어느 계층인지 판별한다. 계층을 섞지 않는 것이 vault가 비대해져도 길을 잃지 않는 유일한 규칙이다.

| 계층 | 무엇 | 저장 위치 | 캡처? |
|------|------|----------|-------|
| **플랫폼** | GenOS 자체 구조·패턴·함정 (모든 고객사 재사용) | `Projects/GenonAI/GenOS/<0X 하위폴더>/` | ✅ |
| **고객사** | 특정 고객 커스텀 결정·맥락 (삼성카드 등) | `Projects/GenonAI/<고객사 폴더>/` | ✅ |
| **세션 상태** | 오늘 진행/대기/다음 작업 | vault 밖 — GenOS 레포 `HANDOFF_NOW.md` | ❌ |

판단 기준: **"이걸 6개월 뒤 다른 세션·다른 고객사에서 다시 보면 시간을 아껴줄까?"** Yes면 플랫폼/고객사 노트, No(이번 작업에만 유효)면 캡처하지 않는다.

- Vault 루트: `~/Library/Mobile Documents/iCloud~md~obsidian/Documents/Note`
- GenOS 영역: `<vault>/Projects/GenonAI/`

### 저장 위치와 허브 대응

플랫폼 노트는 `GenOS/` 바로 아래가 아니라 하위폴더 8개 중 하나에 둔다. 하위폴더 이름이 곧 `00 GenOS 시작하기`의 섹션 이름이다. 폴더별 대표 태그는 policy `genos_subfolders`에 있다(`jq '.genos_subfolders' ~/.dotfiles/vault/vault-policy.json`). `type/*` 태그는 여러 폴더에 공통으로 있으므로 비교에서 빼고, `feature/*`·domain 태그와 아래 "주로 담는 것" 표를 우선해 고른다. 애매하면 캡처 계획에서 사용자에게 묻는다.

| 하위폴더 | 주로 담는 것 |
|---|---|
| `01 온보딩·로컬개발` | 코드 온보딩, 로컬 기동, 레포 구조 |
| `02 아키텍처·K8s·Istio` | 전체 구조, K8s 리소스, 네트워크·Istio |
| `03 배포·CI-CD` | helmfile·GitOps·CI/CD 배포 |
| `04 서빙·MCP` | 코드서빙·모델서빙·게이트웨이·MCP |
| `05 IAM·인증` | 인증·권한·admin-api/front 권한 흐름 |
| `06 데이터·SDK` | 데이터 소스·분석·SDK |
| `07 패키지·레지스트리` | 이미지·패키지 저장소·반입 |
| `08 운영·런북` | 장애 대응·운영 절차·설정 |

고객사 노트는 고객사 폴더에 두고, 그 폴더 허브의 섹션은 태그로 정해진다(policy `hubs.<폴더>.section_by_tag`). 해당 고객사 `section_by_tag`에 있는 태그를 하나 이상 단다. 허브·MOC 섹션은 `tags` 목록에서 처음 매칭되는 태그로 정해진다. `section_by_tag`에는 `type/pattern` 같은 범용 태그도 있으므로 섹션을 정할 `feature/*` 태그를 `type/*`보다 앞에 둔다. `customer/` 태그는 note-rules.md 5절의 폴더별 표를 따르고 새로 짓지 않는다.

| 고객사 폴더 | 허브 |
|---|---|
| `삼성증권/` | `00 삼성증권 시작하기` |
| `삼성카드/` | `00 삼성카드 시작하기` |
| `삼성카드_모니모/` | `00 모니모 시작하기` |
| `인사연동 배치 분석/` | `00 인사연동 배치 분석 시작하기` |

GenOS 패치노트는 이 스킬이 아니라 `write-genos-patch-notes`가 담당한다. 대응표에 없는 새 고객사가 생기면 폴더·허브 신설과 policy `hubs` 추가를 사용자에게 제안하고, 확인 전에는 만들지 않는다.

## 워크플로우

순서엔 실제 의존성이 있다(중복 확인 → 작성 → 허브 등록 → 처음 읽는 순서 검토). **비협상은 셋이다: ② 작성 전 중복 확인, ⑤ 허브 등록, ⑥ 읽는 순서 검토와 결과 보고.** 나머지는 상황에 맞게 조정한다(후보가 하나면 계획 제시를 짧게, 명백하면 확인 생략).

### 1. 후보 추출 — 이번 세션에서 일반화 가능한 것만
좋은 후보: 비자명한 패턴, 빠지기 쉬운 함정, 협의로 확정된 설계 결정, "문서엔 X라는데 실제론 Y"인 사실. 나쁜 후보: 진행상황, 파일 목록, 커밋 해시, 이번 한정 상태.

### 2. 계층 판별 + 중복 확인 (비협상)
각 후보가 플랫폼/고객사 중 어디인지 정하고, **기존 노트를 먼저 검색**한다:
```bash
VAULT="$HOME/Library/Mobile Documents/iCloud~md~obsidian/Documents/Note"
command ls "$VAULT/Projects/GenonAI/" "$VAULT/Projects/GenonAI/GenOS/"
grep -rl "<핵심 키워드>" "$VAULT/Projects/GenonAI/"
```
같은 주제 노트가 있으면 **새로 만들지 말고 그 노트를 갱신**한다(원자성 유지, 중복 금지).

### 3. 캡처 계획 제시 → 확인
글을 쓰기 전, 무엇을 어디에 쓸지 짧게 보여주고 확인받는다. 길게 묻지 말고 목록만:
```
[캡처 계획]
- GenOS/03 배포·CI-CD/<제목>.md (플랫폼·신규) — <한 줄 요지>
- <고객사 폴더>/<제목>.md (고객사·기존 갱신) — <무엇 추가>
- 허브: vk register로 "00 GenOS 시작하기"의 "03 배포·CI-CD" 섹션 (고객사는 태그로 정해지는 섹션)
- 처음 읽는 순서: <앞/뒤 기준 노트> 사이에 추가 또는 불필요 사유 기록
```
사용자가 "그냥 해" 류면 확인 생략 가능.

### 4. 노트 작성 — 형식은 references/note-format.md
frontmatter 순서·태그는 공통 규칙 `note-rules.md`를, source 식별자·7섹션 spine·Mermaid·문체 규칙은 [references/note-format.md](references/note-format.md)를 따른다. `obsidian-note`와 **공통 규칙은 공유하되 본문 spine은 별도**다(저쪽은 Zettelkasten, 이쪽은 입문자 자기완결 field note). **Tavily 웹 리서치는 생략한다** — 출처는 웹 개념이 아니라 이 세션의 실작업·레포다.

핵심은 **용어를 다 설명하는 것보다, 독자가 궁금한 변화 한 가지를 끝까지 따라가게 하는 것**이다.
- 독자의 질문으로 시작한다. 예: "사이트 values에 replicas를 바꾸면 실제로 어디가 달라질까?"
- 입문·구조 설명은 [references/explanation-example.md](references/explanation-example.md)를 읽고, 한 예시의 **입력 → 읽는 주체 → 변환 → 결과 → 확인**을 이어 쓴다. YAML 전후 모습을 보여주고 누가 작성하는지, 값이 없으면 어떻게 되는지도 설명한다.
- 선행 개념은 그 예시를 이해할 만큼 먼저 풀어준다. 매 문단에 GenOS를 억지로 붙이지 않는다. 절이 끝날 때 실제 구조로 연결되면 된다. 의존성·내부 구현은 기본 흐름 뒤에 둔다.
- 기술 자체의 기능, 저장소의 관리 규칙, 현재 설정, 실제 관찰 결과를 구분한다. 문서와 코드가 충돌하면 어느 한쪽을 숨기지 말고 확인 범위를 적는다.

### 5. 허브 등록 (비협상, 생략 금지)
저장 직후 실행한다.

```bash
python3 ~/.dotfiles/vault/vk register "<노트 절대 경로>"
```

- `added`: 허브의 해당 섹션 끝에 `- [[새 노트]] — <본문 첫 문장>`이 들어간다. 자동 요약이 어색하면 한 줄 요지로 다듬는다.
- 섹션이 의도와 다르면(고객사 노트에서 `type/*`가 먼저 매칭된 경우 등) 허브에서 그 줄을 지우고 `tags` 순서를 고쳐 다시 실행한다.
- `exists`: 이미 등록돼 있다(기존 노트 갱신).
- `unclassified`: 플랫폼 노트가 `GenOS/` 바로 아래에 있거나, 고객사 노트에 `section_by_tag`에 있는 태그가 없다. 위치·태그를 고친 뒤 다시 실행하고, 그래도 맞는 섹션이 없으면 허브에 직접 추가하고 보고한다.
- 새 노트의 `related_notes`에 해당 허브(`[[00 GenOS 시작하기]]` 또는 `[[00 <고객사> 시작하기]]`)를 넣어 양방향으로 엮는다.

### 6. 처음 읽는 순서 검토 + 필요 시 갱신 (검토는 비협상)
등록한 허브의 `## 처음 읽는 순서`(numbered list)를 열어 새 노트나 갱신된 노트가 들어갈 자리가 있는지 판단한다. 이 목록은 허브 전체 목록이 아니라 **처음 보는 사람이 따라갈 최소 경로**다. 역할을 섞지 않는다.

이 단계의 비협상은 **목록을 열고, 위치를 판단하고, 결과를 보고하는 것**이다. 실제 수정은 새 노트가 입문 경로에 들어가야 하거나, 기존 노트 갱신으로 읽는 순서의 의미가 달라질 때만 한다.

판단 순서:
1. 새/갱신 노트가 처음 읽는 사람에게 꼭 필요한지 정한다. 대부분의 노트는 폴더 섹션 등록(5단계)으로 충분하다.
2. 필요하면 "이 노트를 읽기 전에 알아야 하는 노트"와 "이 노트 다음에 읽을 노트"를 잡는다.
3. 그 사이에 `[[새 노트]] — 한 줄 요지`를 추가하거나, 변경이 불필요하면 결과 보고에 사유를 남긴다.

### 7. 검증 + 결과 보고
- **검증**: Mermaid를 썼으면 렌더 검증, `related_notes`의 모든 `[[wikilink]]`는 vault 실존(또는 이번에 함께 만드는 노트)을 확인한다. 추가로 `vk register` 결과(허브·섹션)와 처음 읽는 순서 링크/불필요 사유를 확인한다.
- **설명 검토**: 독자가 "무엇을 바꾸면, 누가 읽고, 무엇이 달라지며, 어디서 확인하는가"를 답할 수 있는지 본문만으로 확인한다. 코드 조각만 있고 설명이 없으면 흐름 설명을 보충한다. 설정 예시와 실제 확인 결과를 혼동시키지 않는다.
- **보고**: 작성/갱신한 노트 목록, `vk register` 결과(상태·허브·섹션), 읽는 순서 변경(또는 불필요 사유), 검증 결과를 요약한다.

## 평가 시나리오 — 스킬이 제대로 동작하는지 보는 법

스킬을 수정했거나 동작 품질이 의심되면 아래 케이스로 판단한다. 전부 통과해야 "좋은 GenOS 지식 캡처"다.

| 시나리오 | 기대 행동 |
|----------|-----------|
| 새 플랫폼 패턴 캡처 | 기존 노트를 먼저 검색하고, 없으면 `GenOS/0X .../` 하위폴더에 새 노트를 만들고, `vk register`로 허브에 등록한 뒤 처음 읽는 순서 위치까지 검토한다. |
| 기존 주제 보강 | 비슷한 주제 노트를 새로 만들지 않고 기존 노트에 흡수한 뒤, 허브 등록(`exists`)과 읽는 순서 변경 필요 여부를 보고한다. |
| 허브 등록만 충분한 변경 | 폴더 섹션 등록으로 discoverability는 충분하고 읽는 순서 변경은 불필요하다고 판단하면, 처음 읽는 순서를 수정하지 않고 이유를 남긴다. |
| 고객사 결정 캡처 | 고객사 폴더에 두고 `section_by_tag`에 있는 태그를 달아 `vk register`가 섹션을 찾게 한다. |
| 세션 상태 캡처 요청 | "오늘 무엇을 했다" 수준이면 vault 노트로 만들지 않고 GenOS 레포 HANDOFF 대상으로 분리한다. |
| GenOS 외 일반 개념 요청 | 이 스킬을 쓰지 않고 `obsidian-note`나 다른 적절한 노트 스킬로 라우팅한다. |
| 입문자가 values에서 Pod까지 질문 | 용어 사전으로 시작하지 않고 한 값의 입력·변환·결과를 전후 예시로 보여준다. 렌더 성공과 실제 Pod 기동 확인은 구분한다. |
| 저장소 지침과 사이트 설정이 충돌 | 각 근거의 범위를 적고 미확인 부분을 남긴다. 관리 방침을 기술적 불가능으로 설명하지 않는다. |

## Gotchas — 여기서 실제로 틀린다

규칙이 아니라 *왜 틀리는지*로 기억하라.

- **허브 등록을 빼먹는다 (1번 실패 모드).** 노트만 쓰고 만족하기 쉽다. 허브에 링크가 없으면 새 세션은 그 노트의 존재 자체를 모른다 — AI는 그래프뷰를 못 보고 허브만 진입점으로 읽기 때문이다. *작성한 노트는 반드시 `vk register`를 실행하고 결과를 보고하고 끝낸다.*
- **플랫폼 노트를 `GenOS/` 바로 아래에 둔다.** 허브 섹션은 하위폴더 이름으로 정해지므로 `unclassified`가 된다. 01~08 중 하나를 고른다.
- **처음 읽는 순서를 빼먹는다.** 허브 섹션에 링크만 있으면 발견은 되지만, 처음 보는 사람은 언제 읽어야 하는지 모른다. *작성한 노트는 허브의 `## 처음 읽는 순서`에 넣을 위치를 항상 검토하고, 필요할 때만 수정하며, 넣지 않는다면 왜 순서 변경이 불필요한지 보고한다.*
- **중복 노트를 새로 만든다.** 비슷한 주제가 이미 있는데 검색을 건너뛰면 지식이 두 곳에 갈라져 둘 다 신뢰를 잃는다. 작성 전 `grep -rl`로 먼저 찾고, 있으면 갱신한다.
- **세션 상태를 지식으로 착각한다.** "오늘 chat_service 3줄 고쳤다"는 패턴이 아니라 상태다. "6개월 뒤 다른 고객사에서 시간을 아껴줄까?"를 통과 못 하면 HANDOFF로 보낸다.
- **존재하지 않는 노트를 `[[링크]]`한다.** related_notes의 모든 wikilink는 실존 노트 + 이번에 함께 만드는 노트여야 한다. 미존재 링크는 깨진 그래프를 만든다.
- **입문자 친화를 용어 사전으로 만든다.** 정의가 모두 맞아도 값 하나가 어디로 가는지 연결되지 않으면 독자는 이해하지 못한다. 본 흐름에 필요한 개념만 먼저 설명하고, 한 예시를 끝까지 이어간다. 일반 개념 설명 자체는 필요하며 절 단위로 GenOS에 연결하면 된다.
- **쉽게 설명하려다 사실을 바꾼다.** "Helm은 kubectl apply를 해준다", "폐쇄망은 HTTP/OCI를 못 쓴다"처럼 비유나 로컬 선택을 제품 동작으로 단정하지 않는다. 비유 뒤에는 실제 처리 주체와 적용 범위를 적는다.
- **근거를 경로 목록으로 남긴다.** `## 코드·근거`나 `file:line` 표는 아무도 열어보지 않는다. 독자가 레포를 열지 않아도 되게, 설명하는 자리에 실제 코드 조각(첫 줄 경로 주석, 핵심 줄만, 생략은 `...`)과 "여기서 볼 것"을 붙인다. 코드는 실제 파일에서 가져오고 지어내지 않는다.
- **지식 노트에 현장 운영 양식을 넣는다.** 현장 체크리스트·데모 스크립트·체크박스는 지식이 아니라 작업 양식이다. 고유한 함정만 `헷갈리는 지점`에 문장으로 남긴다.
- **기존 노트를 임의로 옮긴다.** 하위폴더가 더 맞아 보여도 기존 파일 이동은 사용자 확인 후에만 한다. 옮기면 허브 링크와 다른 노트의 `[[링크]]`를 함께 확인해야 한다.
- **회사 자산을 건드린다.** 캡처 자동화가 아쉬워도 회사 레포 `.claude/skills/genos-*`는 절대 수정하지 않는다. 모든 자동화는 이 개인 스킬(`~/.claude/`) 안에서 끝낸다.
- **Mermaid를 장식으로 넣는다.** diagram은 하나의 질문(책임 경계·요청 순서·상태 변화·데이터 관계)에 답해야 한다. 줄여주지 못하면 텍스트나 표가 낫다.

## 예시

**예시 1 — 플랫폼 패턴 캡처**
세션에서 "외부 시스템 전송은 BackgroundTasks + dry-run 플래그로 한다"는 패턴을 적용함.
→ `GenOS/08 운영·런북/GenOS admin-api 외부 시스템 로그 연동 패턴.md` (tags: `work/genos`, `type/pattern`, `backend/integration`), `vk register`로 `00 GenOS 시작하기`의 `08 운영·런북` 섹션에 등록, 처음 읽는 순서는 입문 경로가 아니므로 변경 불필요로 보고.

**예시 2 — 고객사 결정 캡처**
"삼성카드 고객관리번호는 CST_MNGT_NO로 넘어오고, 컬럼은 삼성카드 DB에만 추가"가 확정됨.
→ `삼성카드/삼성카드 PIMS 행위로그 연동.md` 기존 노트 **갱신**(중복 생성 X), tags `customer/samsung-card` `feature/pims`. `vk register`는 `exists`(이미 `00 삼성카드 시작하기`의 `PIMS 행위로그 연동` 섹션에 있음).

**예시 3 — 캡처 거부**
"오늘 chat_service_service.py 3줄 고치고 커밋함" → 세션 상태. **캡처하지 않고** HANDOFF로 안내.
