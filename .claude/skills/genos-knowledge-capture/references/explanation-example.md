# 입문 설명 예시 — 설정 한 줄의 행선지 보여주기

입문·구조 노트를 작성할 때 읽는다. 아래는 설명 방식의 예시이며, 실제 파일 경로·기본값·조건은 대상 저장소에서 다시 확인한다. 단일 결정 기록에 이 길이를 강제하지 않는다.

## 설명을 시작하는 질문

"사이트 values에서 replicas를 2로 바꾸면, 그걸 Kubernetes가 바로 읽는 건가?"

독자는 Helm의 모든 기능보다 **내가 적은 값이 실제 실행 상태로 이어지는 과정**이 궁금하다. 이 질문을 먼저 풀고 의존성 차트나 병합 함수의 세부 구현은 뒤에서 다룬다.

## 아쉬운 설명

> Helmfile은 common과 env를 deep merge하고 releaseKey별 subtree를 추출한다. 관리 필드를 unset한 뒤 Helm이 .Values로 렌더링하며 Kubernetes가 reconcile한다.

용어를 아는 사람에게는 맞는 요약이지만, 처음 읽는 사람은 누가 어느 값을 읽었는지 볼 수 없다. 같은 내용을 더 많은 용어로 확장해도 해결되지 않는다.

## 바꾼 설명

사이트 담당자가 ArgoCD 서버를 두 개 실행하고 싶다고 하자. 아래는 사이트 파일에 추가할 부분만 보여주는 예시다. 기존 파일 전체를 이 내용으로 덮어쓰는 것이 아니다.

```yaml
argocd:
  server:
    replicas: 2
```

Kubernetes는 이 파일을 직접 읽지 않는다. 먼저 저장소의 Helmfile 구성에서 `argocd`에 해당하는 값을 꺼낸다. 바깥쪽 `argocd:`는 여러 설치 대상을 구분하는 이름이고, 이 저장소의 전처리 로직이 그 아래 내용만 해당 차트에 넘긴다.

차트가 받는 값은 다음 모양이다. 앞의 숫자 2가 그대로 이어진다.

```yaml
server:
  replicas: 2
```

Helm은 이 값을 차트의 기본값 위에 덮어쓰고 템플릿에서 `.Values.server.replicas`로 읽는다. autoscaling을 사용하지 않는다는 조건에서 만들어지는 Deployment의 해당 부분은 다음과 같다.

```yaml
spec:
  replicas: 2
```

여기까지는 **적용할 YAML을 만든 것**이다. 설치·업데이트 명령으로 이 내용을 Kubernetes API에 반영해야 컨트롤러가 Pod 수를 맞춘다. `helm template` 출력에서 2를 확인했다고 실행 중인 Pod도 두 개라고 단정하지 않는다.

이 값을 사이트 파일에 적지 않았다면 공통 설정을 확인하고, 거기에도 없으면 차트 기본값을 확인한다. 해당 차트의 기본값이 1인 것을 읽었다면 그 근거를 붙여 설명한다. `enabled` 같은 필드도 비슷해 보인다는 이유로 같은 경로를 탄다고 추정하지 말고 실제 소비 주체를 찾는다.

## 다른 주제에도 적용하는 순서

1. 독자가 하려는 일이나 궁금한 질문을 한 문장으로 쓴다.
2. 같은 이름·같은 값으로 시작과 끝을 잇는다.
3. 단계마다 "누가 작성하고 누가 읽는가, 무엇으로 바뀌는가"를 설명한다.
4. 생략 시 동작과 중요한 조건을 확인된 범위에서 설명한다.
5. 기대 결과와 실제 검증 결과를 분리한다.

가령 ESO 노트도 리소스 종류를 모두 나열하기 전에, GitLab의 변수 하나가 ExternalSecret의 지시를 통해 Kubernetes Secret의 한 항목으로 만들어지고 애플리케이션에 전달되는 과정을 이어 보여준다. 이름만 바꾸어 예시를 재사용하지 말고 실제 처리 주체와 갱신 조건을 확인한다.

## 설명을 단순하게 해도 지켜야 할 경계

- 기술적으로 가능한 것과 저장소에서 선택한 운영 방식을 구분한다. 로컬 차트를 쓴다고 내부 HTTP/OCI 저장소가 불가능한 것은 아니다.
- 비유는 입구로만 사용한다. "설계도" 뒤에 실제 입력·출력·처리 주체를 적는다.
- 근거끼리 충돌하면 그 사실을 남긴다. 오래된 안내 문장 하나로 현재 사이트 설정이나 관찰을 지우지 않는다.
- 코드 경로는 근거 영역에서 찾게 하되, 핵심 동작의 설명까지 근거 표로 미루지 않는다.
