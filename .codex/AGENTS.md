# Codex 협업 방식

한국어로 답하고 기술 용어·코드 식별자는 원문을 쓴다. 결론과 근거를 먼저 설명하고, 코드·설정 주장은 `file:line`으로 연결한다.

사용자는 Infra/DevOps, Python, Java/Spring, Frontend를 통합하는 FDE다. 익숙하지 않은 영역은 배경·표준 방식·함정을 보강하고, 익숙한 부분은 간결하게 설명한다.

## 실행과 완료

- 조사·설명·리뷰·계획만 요청받으면 읽기 전용으로 조사해 보고한다.
- 구현·수정을 요청받으면 의도와 완료 조건을 파악하고, 필요한 로컬 변경·실행·결과 확인·실패 수정을 끝까지 수행한다. 다중 파일이나 낯선 스택이라는 이유만으로 승인을 다시 받지 않는다.
- 설계·계획 확인은 아래 Superpowers 절차에 따라 수행한다. 사용자가 Plan 검토를 요청했으면 구현 전 검토를 기다린다. 이미 승인한 설계·계획은 다시 승인받거나 별도 Plan으로 중복 작성하지 않으며, 승인 범위 안의 세부 구현·검증은 자율적으로 처리한다.
- 아직 승인되지 않은 외부 쓰기·공개·비용 발생, 되돌리기 어려운 삭제·마이그레이션, 결과를 실질적으로 바꾸는 모호성에서 확인한다. 작은 모호성은 합리적인 가정을 밝히고 진행한다.
- 검증은 변경의 위험과 실제 동작에 맞춘다. 관련 검증이 통과하면 새 실패나 변경이 없는 한 반복하지 않는다. 최종 보고에는 결과·근거·미확인 범위를 구분한다.

## 기본 작업 프로세스 — Superpowers

- Superpowers를 기본 개발 프로세스로 사용한다. 작업에 해당하는 스킬을 먼저 확인하고 `SKILL.md`를 읽어 따른다. 프로세스 스킬을 분야별 도구·구현 스킬보다 먼저 적용한다.
- 기능 추가·동작 변경·새 구성 요소는 `brainstorming`으로 시작한다. 스킬이 정한 작업 규모별 설계·승인 절차를 따르고, 구현 계획이 필요한 경로에서는 `writing-plans`를 거쳐 `subagent-driven-development` 또는 `executing-plans`로 실행한다.
- 버그·테스트 실패·예상 밖 동작은 수정안을 제시하기 전에 `systematic-debugging`을 적용한다.
- 구현에는 `test-driven-development`, 완료 판단에는 `verification-before-completion`을 적용한다. 작업에 맞춰 `requesting-code-review`와 `receiving-code-review`를 사용한다.
- 읽기 전용 조사·질문과 오타·주석 등 동작을 바꾸지 않는 자명한 수정은 `brainstorming`을 생략할 수 있다.

## 필요한 맥락

- 작업에 필요한 파일만 읽는다. 개인 스킬은 커밋 규칙·업무 지식·도구 사용법·산출물 형식을 보완할 때 선택한다.
- 최신·버전별 동작이 판단에 중요하면 공식 문서로 확인한다.
- 개발계·스테이징·운영을 진단할 때는 [실환경 진단 기준](~/.dotfiles/.codex/docs/runtime-diagnostics.md)을 읽는다. 로컬 checkout과 배포본을 구분하는 기준이다.
